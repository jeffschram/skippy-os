1. Concept

The old Skippy spent most of its effort rebuilding things the Claude app already does: chat history, the agent runner, approval cards, a skills store, session tracking. In this version, Claude is the workspace. My projects live there, and that's where deep work happens, on the Mac or from my phone.

Skippy OS keeps two things Claude doesn't have:

  • A durable knowledge system (Convex): projects, tasks, people, notes, events and their status, outside any single chat.
  • A web app that shows all of it in one place. I can fully edit it, capture into it, and chat with it to turn ideas into real things.
Principles
  • Don't rebuild the Claude app. Before adding a feature, ask: does Claude desktop or iOS already do this? If yes, link to it instead.
  • Convex is the one shared record. Claude and I both write to it: Claude through the Skippy MCP, me through the web app. Every write records who made it.
  • Claude reports as it works. A Skippy skill and each project's instructions tell Claude to record status. The dashboard is only as fresh as those reports, so staleness is shown, not hidden. decided
  • Structured, not dumped. An importance bar, accept directly, provenance on everything. borrowed
  • Tasks are actions. dueAt is only an action deadline. borrowed
  • Built for Claude, open to any harness. Skills and workflows target Claude. The Skippy MCP is a public OAuth endpoint (Clerk), so Claude, ChatGPT, Codex and anything else that speaks MCP can connect. decided

MCP access via OAuth (Clerk) decided

Any MCP harness can connect: Claude (desktop, iOS, claude.ai, Code), ChatGPT, Codex and others. Requirements:

  • Transport: Streamable HTTP at https://<project>.vercel.app/api/mcp. That exact URL is the OAuth resource. Use the stable production alias, never a per-deploy preview URL.
  • Discovery: protected-resource metadata at /.well-known/oauth-protected-resource, advertised in WWW-Authenticate challenges borrowed
  • Authorization server: a new Clerk instance just for Skippy OS (not the old project's), which also signs me into the web app
  • Client registration:
    • Dynamic client registration (DCR). Claude Code needs it: a connector in this session failed with "does not support dynamic client registration".
    • Client ID metadata documents (CIMD) for ChatGPT
    • Pre-registered clients as the fallback
  • Flow: authorization code with PKCE S256, consent on, refresh through offline_access
  • Scopes: skippy:read and skippy:write. Each tool declares which it needs.
  • Tokens: JWT access tokens whose aud is exactly the MCP resource URL. Verified by RS256 signature against Clerk's JWKS, plus issuer, expiry and token type. Never loosen audience checks to make a client work. borrowed
  • Identity: the Clerk subject maps to the single owner. Unknown accounts are rejected, never auto-created.
  • Gateway: the MCP route signs each operation into a one-use, short-lived Convex gateway call. Convex rechecks scopes and ownership. borrowed
  • Static tokens: for unattended callers only (the chat runner and local connectors). Each is hashed and has a required role.
Lesson: the old project built all of this, but it never went live. The Clerk setup was never finished: automatic client registration wasn't advertised, the Skippy scopes didn't exist, and tokens tied to the MCP's URL were never confirmed. So here, OAuth is Phase 0: prove it end to end before building any other tools.
Phase 0 acceptance: an OAuth spike before building any other tools

Deploy /api/mcp with just two tools: whoami (read) and capture (write). Then for each client below, run discovery → sign-in and consent → one read → one write → read it back → refresh → reconnect:

  1. Claude Code (DCR)
  2. claude.ai custom connector, then use it from Claude iOS
  3. Claude desktop
  4. ChatGPT (CIMD or pre-registered)
  5. Codex

Negative checks: an expired token, a wrong audience, a read-only consent attempting a write, and an unknown Clerk account. Record which registration mode each client used. A client that fails is listed as unsupported; it is not worked around by loosening validation.

4. Claude-side setup

Skippy plugin the behavior lives here

A Claude plugin, versioned in this repo, bundling the Skippy MCP config and these skills:

  • skippy-status: when and how to record project status (see below)
  • skippy-capture: how to file a thought, link or person from any chat
  • skippy-morning: a scheduled pass. Read Gmail, Calendar and iMessage since the last cursor, ingest what clears the rubric, and write a briefing note.
  • skippy-weekly-review: flag stale projects, overdue tasks and goal check-ins
  • skippy-plan-project: turn a brief into phases and tasks in Skippy
  • skippy-nightly-sweep: catch unreported activity in code projects (see below)
How status gets recorded decided
  • Every Claude Project gets a line in its instructions: Skippy project: <slug>. Follow the skippy-status skill. Every Code folder gets the same line in its CLAUDE.md.
  • The skill says to call record_project_status when a milestone is reached, a decision is made, something gets blocked, or a working session ends. It also says to create or complete tasks as they come up.
  • Risk: Claude sometimes forgets. Mitigation (proposed): the dashboard shows "last update from Claude" on every project and flags active projects with no update in 7 days (adjustable in settings). The weekly review then asks about them. decided
  • Nightly sweep decided: a scheduled task in Claude desktop on the mini runs the skippy-nightly-sweep skill. For each active code project it reads git commits and branches since the last sweep, plus local Claude Code session transcripts for that folder. Wherever there's activity Claude didn't report, it records a status update with actor: {kind: "claude", surface: "scheduled"}. Each project keeps a lastSweptAt marker, so nothing is double-counted.
  • Limitation: Claude Projects (chat) conversations can't be read by a sweep, because there's no API for them. Life and general projects rely on the skill and the 7-day flag only.
Linking a Skippy project to its Claude home

Each project stores where it lives in Claude: a Claude Project name or URL for life/general projects, or a Code folder path on the mini for code projects. The dashboard shows an "Open in Claude" link. Open: whether Claude supports deep links that open a Project directly on iOS.

5. Web app functionality

5.1 Home input: one box, two modes decided
  • Enter: a quick capture. It's saved immediately with no reply and needs no Mac mini. Text, URLs and files are all supported. borrowed
  • Chat mode (a toggle, or starting the message with /chat): starts or continues an idea chat with Claude
  • Captures are processed later by the morning pass, or by Claude if a chat picks them up
  • "Hold" captures, a private 7-day hand-off between devices, are kept borrowed
5.2 Idea chat & promotion decided
  • While chatting, Claude spots things that could become real records and shows inline promotion cards, such as "Create task: renew passport · due Mar 1" or "New project: Garden redesign".
  • Cards have editable fields (title, due date, project, area). One click creates the record.
  • Card types: task, event (a Skippy-local event), project, note, person, recurrence
  • Promoting to a project: the chat moves to the new project as its origin history. Claude writes a summary of the idea that seeds the project's notes. The new project page then offers to set up its Claude home: a Claude Project or a Code folder.
  • Ignored cards simply expire. avoid letting this turn into a triage queue: cards exist only inside the chat they came from, and nothing piles up anywhere.
5.3 Chat on any item decided

Every item's details view (task, project, person, note, event) has a chat scoped to that item. Claude gets the item, its links and recent activity as context. The project chat includes the history promoted from the idea chat.

5.4 Dashboard
  • Projects board: status, health, last update from Claude (with a staleness flag), next tasks, and a link to its Claude home
  • Today: tasks due or scheduled, events, recurrences coming up, and waiting-on items. Deterministic, with no LLM call. borrowed
  • Overnight: what Claude recorded since I last looked, from the activity feed
  • Ingestion health: when each source was last covered and any errors
  • Briefing: the latest morning note. When the morning pass finishes it also sends a web push ("Your briefing is ready: 3 due today, 1 overdue"), and tapping it opens the dashboard. decided On iPhone, web push only works when the web app is added to the Home Screen, so the app ships as a PWA. Quiet hours and deduping are borrowed.
5.5 Full editing decided
  • Create and edit everything: projects, phases, tasks, notes, people, companies, events, recurrences, goals
  • Every write records an actor: me, or Claude plus where it ran. Claude can call get_changes_since to see what I changed in the dashboard.
  • Conflicts: last write wins per field, and the activity log shows both writes. Since Convex is the only store, there's nothing to sync.
5.6 Knowledge, people, agenda
  • Brain: notes, links, memories, decisions, principles, all in one knowledge table, with search borrowed
  • People and companies as a light CRM
  • Agenda: Skippy events plus Google events (inbound-only), and recurrences borrowed

6. Chat engine decided

Claude Code sessions on the Mac mini
  1. I send a message. Convex saves it and queues a chatTurn.
  2. The chat runner on the mini claims the turn (lease-based borrowed) and resumes that chat's Claude Code session, or starts a new one.
  3. The session gets the Skippy MCP (with a propose_promotion tool), local connectors, and Claude's own connectors. It has the chat's scope as context.
  4. Streamed events write to chatTurnEvents, which the UI shows live. Promotion cards are tool results rendered as UI.
  5. Working folder: for a code project's chat, the project's Code folder, read-only decided. The chat can read code to answer questions or plan, but it can't edit files or run shell commands. Code changes happen in a real Claude Code session. For everything else, a neutral scratch workspace.
When the mini is offline or busy decided

The message is saved and shows "waiting for Mac mini", based on the host heartbeat. It runs when the mini comes back. Quick capture and all editing keep working.

Runner scope: chat only

The runner only runs chat turns. No task runs, worktrees, publish steps, closeouts or scheduled agent passes; those are Claude desktop's job now. It reuses the old patterns for host token, heartbeat, lease, stall watchdog and explicit MCP injection. borrowed

Lesson: the old runner grew four claim loops and most of the reliability incidents. Keeping it to one loop is the point of this concept.
Web chats vs Claude app chats decided

Web app chats are Claude Code sessions on the mini, so they don't show up in the Claude app's chat list.

Any chat has a Continue in Claude button. It has Claude write a brief: the goal, decisions so far, open questions, and the linked Skippy records with their IDs, ending with the Skippy project: <slug> line. The brief is saved to the project's notes (or as a note, if there's no project) and copied to the clipboard, ready to paste into a new Claude Project or Code session. The chat then shows "continued in Claude" with the date.

8. Skippy MCP

Tools (kept small)
  • Status: record_project_status, get_project, list_projects
  • Records: upsert_task, complete_task, upsert_project, create_phase, upsert_person, upsert_knowledge, create_event, upsert_recurrence, complete_recurrence, link_entities
  • Capture & ingest: capture, list_captures, ingest_object, get_importance_rubric, get_source_cursor, advance_source_cursor
  • Read: search, get_context_bundle, get_today, get_changes_since
  • Web chat only: propose_promotion

Who can use which tools:

  • Harnesses signed in through OAuth get tools by scope: skippy:read for reads, skippy:write for writes.
  • Unattended callers use static tokens with a role: chat (the chat runner, which also gets propose_promotion) and ingest (local connectors).
  • Tools outside your scope or role are never even listed. borrowed

Phase 0: OAuth test
  • A new Clerk instance, a Vercel project and a Convex deployment
  • /api/mcp with two tools, whoami and capture, plus protected-resource discovery and the signed gateway
  • Clerk configured for DCR, CIMD, the two scopes, and JWT access tokens bound to the MCP URL

Done when: the §3 acceptance run passes in Claude Code, claude.ai and iOS, and Claude desktop, and the negative checks fail as they should. ChatGPT and Codex either pass or are written down as unsupported, with the reason.

If Clerk can't do it: stop and decide before Phase 1. The fallback candidates are a different authorization server in front of the MCP, or static tokens only. Open

Phase 1: Foundation
  • pnpm monorepo: convex/, apps/web, packages/shared; pnpm check; CI deploys Convex
  • Schema for projects, phases, tasks, goals, areas, people, companies, knowledge, relationships, source refs and activity events, with Actor on every write
  • Web app shell with Clerk sign-in, limited to the owner
  • MCP tools: the status, records and read groups from §8

Done when: from a Claude chat I can create a project and a task, read them back, and see both in the activity log with Claude as the actor. pnpm check passes.

Phase 2: Import
  • A snapshot export of the old deployment, and scripts/import-v1/ with the §10 table mapping
  • A dry-run mode that prints the counts without writing

Done when: the per-table counts (exported, imported, skipped with reasons) add up, 10 records of each type pass a spot check, no code project or code task came across, and importMap has been dropped.

Phase 3: Status loop the first usable version
  • The Skippy plugin, with skippy-status and skippy-capture
  • The Skippy project: <slug> line added to each Claude Project and each Code folder's CLAUDE.md, and claudeHome filled in
  • Dashboard: the projects board with health and the 7-day stale flag, Today, and Overnight
  • Project and task pages, the shared item details view, and full editing
  • get_changes_since, so Claude sees my dashboard edits

Done when: after one week of normal work, every project I touched has a status update I didn't ask for, and a change I make in the dashboard is picked up by Claude in its next session on that project.

Phase 4: Capture & brain
  • The Home input in capture mode, including files and "hold" captures
  • /brain sections, people and companies, and /agenda with Skippy events and recurrences
  • Embeddings and search, in the web app and through the MCP

Done when: a capture made on my phone is findable by search from a Claude chat, and completing a recurrence in either place advances it exactly once.

Phase 5: Idea chat
  • The chat runner on the mini: host token, heartbeat, lease-based claiming, stall watchdog, explicit MCP injection
  • Chat mode on Home and chat on any item, with live streaming
  • propose_promotion and promotion cards; promoting a chat to a project; "Continue in Claude"
  • "Waiting for Mac mini" when the host is offline. Code-project chats read-only.

Done when: an idea typed on my phone becomes a project with two tasks through cards alone; a message sent while the mini is off runs after it comes back; and killing the runner mid-turn leaves the chat in a clear failed or retry state, not stuck.

Phase 6: Morning briefing
  • Source cursors and receipts; the skippy-morning skill as a scheduled task in Claude desktop on the mini
  • Sources, one at a time, each with its own acceptance evidence: Google Calendar (inbound), Gmail, then iMessage through a local connector
  • The briefing note, the ingestion health tile, PWA install, and web push with quiet hours and dedupe

Done when: for seven mornings in a row the briefing arrives by push at the set time, each source's cursor has advanced with no gaps, and re-running a pass creates no duplicates.

Phase 7: Sweeps & reviews
  • skippy-nightly-sweep for code projects, and skippy-weekly-review
  • Stale projects surfaced in the weekly review

Done when: commits made in a session where Claude didn't report show up as a status update the next morning, marked as coming from the sweep, and never twice.
