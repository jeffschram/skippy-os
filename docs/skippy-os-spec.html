1. Vision & principles

Skippy OS is one place for everything I need to know, decide and do. AI agents running locally keep it current: they pull in email, calendar and messages, turn them into structured knowledge and tasks, and do delegated work. The web app is where I look, decide and steer.

This is a fresh project. It borrows proven patterns from the older ~/src/skippy-mcp-and-app, but it shares no code, Convex deployment or data with it. See §10.

Core principles
  • Structured, not dumped. Ingest objects (tasks, people, notes, decisions), not raw text. Every object keeps provenance (source refs). borrowed
  • An importance bar, then accept directly. A rubric decides what is worth saving. If it's unclear, skip it. Whatever clears the bar is accepted, with no approval queue for knowledge. avoid the old triage and memory-review gates, which were all retired.
  • Tasks are actions. A dated event is not a task, and dueAt is only an action deadline. Candidates carry itemIntent (action | event | reference) and dateKind (deadline | event). borrowed
  • One place to look. Home is the single queue. Attention is derived at read time, not managed in parallel review queues. avoid the competing Attention / Review / Resurfacing surfaces.
  • Approvals are for side effects only. Agents read, write knowledge and draft freely. Sending, paying, pushing and deleting externally need my OK.
  • Convex holds all state. The runner is restart-safe and keeps nothing that Convex can't rebuild. borrowed
  • Deterministic before AI. Summaries, the Today model, attention and closeouts are plain code. LLMs are used where judgment is needed. borrowed
  • Write the real scope down. The old PLAN said no recurrence, no chat and no file storage, and all three got built anyway. This spec includes them from the start. avoid
Non-goals (for v1) Open
  • Multi-user or team collaboration (single owner)
  • Native mobile app (PWA first)
  • Writing to Google Calendar. Skippy owns its own agenda and reads Google inbound-only. avoid the duplicate bookings from 2026-09.
  • 3D "Mind" graph browser (maybe later)

3. Functionality

3.1 Capture get things in, fast
  • Quick capture from the Home bar, ⌘K, an iOS Shortcut or share sheet, email-to-Skippy, or voice. Text, URLs and files are all supported.
  • intent: remember (the next agent pass ingests it) or hold (a private 7-day hand-off between devices). borrowed
  • Agents process captures into objects directly and record what they made. There is no accept/reject step. avoid approval queues.
3.2 Second brain (knowledge) notes, links, memories, decisions, principles
  • One knowledge table with a kind field. borrowed. The old project spent a migration consolidating separate tables into one; we start unified.
  • A typed relationship graph between any entities: person ↔ project ↔ note. borrowed
  • Semantic plus keyword search (vector index filtered by embedding model)
  • "Ask Skippy": an answer from the brain with citations. It runs as a chat turn on the runner.
  • People and companies as a light CRM, including a "reach out" cadence
3.3 Projects projects → phases → tasks
  • Projects have a kind (code | general), phases, a notes pad with snapshots, a file library and decisions. borrowed
  • Code projects keep their execution settings (local path, preferred harness, verify command) on the project itself. The old project used a separate mapping, and the owner asked to move it onto the project page.
  • The loop is plan → brief → ready → execute → review → closeout. borrowed
3.4 Life tasks, recurrences & waiting-on
  • Tasks outside any project, grouped by Area, with commitment (must | want) borrowed
  • Recurrences use an interval or an RRULE, anchored either to completion or to schedule, with lead time, idempotent complete/skip and capped history borrowed
  • Waiting-on: a task can wait on a person and gets nudged. A nudge only drafts an outbound action.
3.5 Home (Today) the single queue
  • Sections: Summary → Today (including 7 days of overdue) → Upcoming (the next 7 days) → All borrowed
  • Row kinds are task | event | recurrence | review, keyed by {kind, id}. Reads are bounded and paginated with seek cursors.
  • The Summary is deterministic count clauses ("3 due today, 1 overdue, 2 approvals"), with no LLM call
  • "Waiting on me": approvals, failed runs, and items whose review date has come up
  • One shared item-details modal with per-item chat borrowed
3.6 Attention (derived)
  • Statuses: immediate | todo | in_progress | scheduled | ok | stale | unassessed. They are computed at read time from due dates, status and activity. borrowed
  • A manual override with a reviewAt date wins until that date. This replaces "memory review": nothing needs approving, but things can resurface.
3.7 Agent delegation & chat
  • Delegate any task. Its brief and acceptance criteria are copied onto the run when it is queued.
  • Chats exist per project, per item and per page. They are a first-class feature, not something added later. avoid the old drift into "project chats" that also served pages.
  • Chat history stays with the chat when you switch harness, which fixes an owner complaint from the old app
  • Scheduled agent roles: agenda (ingestion), PM per project, task executor, weekly review, and maybe finance

Details in §6.

3.8 Goals, areas & check-ins
  • Areas are configurable data rather than enums, and goals roll up to them
  • Interviews / check-ins: guided Q&A templates (project, goal, person, decision, weekly review) whose answers become knowledge borrowed
3.9 Finance Open
  • If included: Plaid-fed accounts, transactions, daily balances, budgets and debts, with money in integer cents and a monthKey borrowed
  • Categories and account owners are configurable data. avoid personal names hard-coded as schema literals.
3.10 Notifications & activity
  • Web push (PWA), with dedupe keys, quiet hours and a daily digest borrowed
  • An Activity log of everything agents and I did, including outbound actions that ran

4. Data types

Convex tables. Every table also has _id, _creationTime and updatedAt. Single owner: Open whether to keep an ownerId on every row, which would be cheap insurance.

Shared validators (packages/shared, defined once)

{ entityType, entityId: string }. entityType is one of goal | project | task | knowledge | person | company | recurrence | event. It is defined once and imported everywhere. avoid the three copies the old project had.

6. Agent runner

How it runs work borrowed
  1. A launchd daemon on the mini. Connections are outbound only, it authenticates with a host token, and it heartbeats to renew leases.
  2. Separate claim loops for runs, chat turns and agent passes. Each claim is atomic and lease-based.
  3. Task runs: make a worktree (one per run, under an allowlisted root), run the harness turn, verify, publish (commit, push, PR, with approval), then in_review. Each step writes durable status and events.
  4. Agent passes: a one-line prompt ("load your skills via get_skill and follow them"), a role-scoped MCP token, a hard 15-minute timeout, and retries at 1, 5 and 15 minutes that respect quiet hours.
  5. Chat turns: no worktree. Run in the project checkout, with approval cards for gated actions.
  6. Closeout: a deterministic post-merge ritual. Verify the merge, pull, remove the worktree and branch, then mark the task done.
Harness adapters borrowed
  • A shared HarnessAdapter interface: start/resume, an event stream, approval requests, usage
  • Claude: the Agent SDK. Codex: codex exec --json in a workspace-write sandbox.
  • The Skippy MCP is injected explicitly per session. A host-level claude mcp add silently vanished on 2026-08-18.
Reliability rules borrowed
  • A stall watchdog aborts silent sessions. Sessions were stranded in 2026-08.
  • On restart, active runs are marked interrupted, never auto-resumed
  • Process-level backstops for SDK teardown errors
  • Concurrency limits from agentHosts.capabilities, a daily cost cap Open, and a kill switch
Runner policy Open
  • A default harness per task kind or role?
  • Should the runner run as a dedicated macOS user rather than the owner? The old one ran as the owner.

8. Engineering conventions borrowed

Carried over from the old CLAUDE.md
  • pnpm workspaces, ESM, node ≥ 20. pnpm check (typecheck and test) is the single gate.
  • Colocated tests (foo.test.ts). Pure logic goes in *-helpers.ts so it's testable without React or Convex.
  • Comments explain why, including incident dates
  • Bounded, indexed reads from day one, with no .collect() then slice. The old project hit Convex's 32k document-read limit.
  • Derive at read time instead of storing or backfilling (online status, default paths, attention)
  • Agents work on agent/<topic> branches, and only the owner merges
  • Never convex deploy by hand. CI deploys.

10. Borrowed vs avoided from skippy-mcp-and-app

A digest of the old project (515 commits, 60 tables, 83 MCP tools), read on 2026-11-18.

borrowed Patterns that worked
  • Lease-based claiming (claimToken, claimVersion, leaseExpiresAt) with cooperative cancelRequested
  • Idempotency everywhere: sequence numbers and high-water marks on events, request IDs on occurrence actions, receipts on ingestion, dedupe keys on notifications, harnessRequestId on approvals
  • Convex holds all state; the runner is restart-safe, and interrupted runs are never auto-resumed
  • Settings are frozen onto the run when it is queued
  • Deny-by-default role allowlists, and hashed tokens shown once
  • Skills as versioned behavior; the runner only schedules and supervises
  • Deterministic Summary, Today model, attention and closeout
  • Canonical {kind, id} identity, seek pagination, and a shared item modal with chat
